# Security audit and maintenance plan

**Review pin:** upstream `goncharik/hermes-mobile` commit `e1b8dd5f60ad25d08735b6035f8ffda9c18d5f9b`. The detached upstream audit checkout was read-only. The Swagatar-LLC fork began at this exact SHA. This report describes source and tracked history, not a built/signed app, deployed server, push plugin, private relay, or TestFlight binary. **Decision: hold production adoption.** No covert third-party egress was confirmed in reviewed iOS paths; this is not a statement that the full system is safe.

## Trust boundaries

The iPhone keeps Hermes credentials in Keychain and transcripts in SQLite; it sends chats, attachments, microphone transcription, and approval decisions to a user-configured gateway. A high-privilege agent executes approved work. Relevant adversaries are an on-path observer of unprotected HTTP, an actor with device/backup access, a compromised plugin/update source, or another client changing the approval queue. A properly authenticated encrypted tailnet reduces on-path risk but a local-looking hostname is not proof of transport encryption or destination identity. Server-side authorization, actual gateway deployment, and relay data handling remain unknown.

## Supply chain and negative checks

MIT permits our fork with the upstream license notice. `HermesKit/Package.resolved` pins 16 Swift dependencies, but `Project.swift:18-24` uses package ranges and `docs/development.md:111-166` describes manual distribution; the tracked tree has no app release attestation or CI workflow. Tuist setup is unversioned (`docs/development.md:6-10`). Actual TestFlight/App Store provenance, Apple signing custody and relay ownership are unknown. The publisher-operated push relay is private according to `docs/features/push-notifications.md:8-13`; the iOS fork alone does not control it.

Read-only gitleaks history and TruffleHog filesystem scans found no confirmed secret; two gitleaks prose hits were false positives. Syft enumerated the Swift pins; Grype found no match in its available database. OSV could not parse the Swift lockfile, so its coverage is unknown. ShellCheck was clean. Semgrep was available but not run across the full tree. Native Markdown rendering showed no WebView execution; OAuth loopback validates state and uses PKCE; snapshot SQL binds parameters. These checks do not prove absence of vulnerabilities or validate runtime data flows.

## Maintenance gates

1. Review the first security PR's diff and package tests. Do not merge or deploy merely because static tests pass: the approval FIFO race and device network behavior remain open.
2. Before enabling push, separately audit the exact plugin commit, dependency versions, Hermes update endpoint, publisher relay destination/retention, and APNs identity. Keep one-tap moving-branch updates disabled; pin a reviewed immutable plugin revision.
3. Resolve request-bound approval with the server; if unavailable, consider disabling positive mobile approval. Then handle cache/logout and test actual network redirects, HTTP warnings on saved sessions, device protection and backups.
4. Keep `upstream` configured but review each upstream diff before merging. Pin the toolchain and app dependency resolution, add CI and signed release provenance on protected commits, and enroll our Apple team only after an explicit signing/distribution decision. Never auto-merge upstream into a signed release.

**Verification limits:** `HermesKit` tests exercise the client package, not the iOS layout or device networking. Tuist is absent locally, so the iOS card-layout test was not run. A reviewer independently identified the approval FIFO race after the client-only change; this remains an explicit hold, not a passing check. Strongest case for a controlled trial is the native client, MIT rights and no confirmed hidden egress in reviewed iOS source. Strongest case against production adoption is the unowned plugin/relay and unbound approval protocol.
